# ue5/ STATUS (2026-10-09; WP-UE-01 bridge rebuild 2026-11-13)

## What works

- **UE 5.8 C++ project `KspUe5`** (no Blueprints): game module `KspUe5`, editor module `KspUe5Editor` (map-generating
  commandlet), plugin `KspCoreBridge`. Builds from the command line for Development Editor and Development Game, Win64, with 0
  warnings in project code. Git repo in `ue5/` with an Unreal `.gitignore` and `.gitattributes` (binary `.uasset`/`.umap`/`.lib`/`.png`).
- **KspCoreBridge** links the real core (WP-UE-01, 2026-11-13): `kspcore.lib` (RelWithDebInfo, `/MD`, IDL 0, C++20) and `Jolt.lib`
  through the **link manifest** the core build writes (`core/build/RelWithDebInfo/kspcore_link.txt`, `file(GENERATE)` in
  `core/src/CMakeLists.txt`; `key=value` lines: `manifest_version`, `config`, `include`, `lib` in link order, `define` for Jolt's
  `JPH_*` configuration). `KspCoreBridge.Build.cs` reads it (env `KSPCORE_LINK_MANIFEST` overrides), so a new core dependency never needs
  a Build.cs edit; the `ue5/Stub` placeholder stays behind `bUseRealCore = false`. Both targets (Development Editor, Development Game)
  build from clean with 0 warnings (lines containing "warning" in the UBT logs: 0). The module compiles with `FPSemantics = Precise`
  (property verified in `ModuleRules.cs:784` of the engine's UBT sources); every call into core goes through `FKspFpGuard`, which sets
  MXCSR to 0x1F80 (round to nearest, exceptions masked, FTZ / DAZ off) and restores the caller's value. The core's test-only C ABI
  (`kspcore_test.h`, outside `KSPCORE_ABI_VERSION`) gives the Jolt pile scenario hash, an MXCSR probe and a Jolt configuration probe.
  Jolt needs an AVX2 CPU. Required compiler settings are in README.md.
- **Headless automation tests**: 5 / 5 pass, run twice after the clean builds (`KspUe5.Bridge.LinksCore`, `KspUe5.Bridge.FpGuard`,
  `KspUe5.Bridge.JoltStep`, `KspUe5.Precision.Float32VsLwc`, `KspUe5.Spike.CubeSpherePatch`). `JoltStep`: the pile scenario
  (96 bodies, 200 steps, Jolt double precision) gives state hash `0x0be3de1d6affe387` through the bridge and the same value in its ctest
  twin `capi.jolt_step` (a pure C program on the same test ABI; it writes `core/build/RelWithDebInfo/kspcore_jolt_step.txt`, which
  `Scripts/test.ps1` regenerates before each run); the hash is also identical at 4 threads, run to run, and with the caller's MXCSR set to
  FTZ / DAZ. Jolt is deterministic per binary and call order, not across compilers, so the hash is only compared between processes that
  run the same `kspcore.lib` / `Jolt.lib`; no hash is stored in the repo.
- **Map `/Game/Maps/ScaleSpike`** is generated by code (`-run=KspCreateSpikeMap`). All content is spawned at runtime in C++.
- **Phase-0 scale spike**: runs unattended and deterministically in about 3.5 minutes. It writes CSVs, PNGs and a log, then quits.
  Results are in `spike/RESULTS.md`.

## Spike verdict (details in `spike/RESULTS.md`)

- **Jitter-free at Kerbin scale: YES**, with LWC alone and no rebasing, provided every primitive stores vertices relative to a
  nearby origin. Measured on the GPU output: 0.000 px at a 100 km orbit, at 1 m above the ground and at 12,000 km (Mun); at most
  0.048 px while strafing 1 mm per frame; 0.000 px pop on a forced origin shift. The Mun renders at 12,000 km and is stable to
  0.11 px with the camera moving at 112 km/s.
- **The one failure mode** is geometry stored far from its primitive origin (for example a planet-centred mesh): 7 to 19 px of
  jitter, and rebasing does not fix it. A UE4/Unity-style float32 pipeline would jitter 5.6 cm (13 to 17 px) at Kerbin's surface
  and 72 cm (207 px) at the Mun. That is the classic reason KSP rebases, and UE 5.8's double-float vertex path removes it. The
  op-for-op emulator of that path was validated against the GPU.
- **Rebasing**: both `UWorld::SetNewWorldOrigin` (manual) and moving every actor work in 5.8. `SetNewWorldOrigin` is cheaper:
  0.23 ms per shift bare, 5.9 ms per shift (+9.1 ms game thread) with 457 bodies + 1,325 colliders, against about 5.5 ms for
  KSP's per-tick shift. Chaos does not support origin shifting, so bodies are teleported one by one, which is about 80% of the
  cost. Recommendation: no per-tick rebasing. Use camera-local placement from the core's doubles, and rebase rarely (about a
  100 km threshold) only where a float-only subsystem needs it.

## What does not work / blockers

- `UnrealBuildTool.exe` cannot be run directly: it needs the .NET 10 runtime, which is not installed system-wide. Workaround in
  place: everything goes through `Build.bat`, which uses the engine-bundled dotnet. Not a blocker.
- Observed once, not reproduced: the very first full automation run in the fresh worktree stalled (the game-thread frame counter stopped
  advancing, no test started) and was stopped after about 6 minutes; five later runs (3 single tests, 2 full) were fine. Cause unknown.
- Fresh core suite (`core/build` deleted, `run_tests.ps1`, 4 jobs, two other agents building): build 1,206 s, ctest 52 / 54 in 897.7 s. The two
  failures were `unit.random_order.27` and `unit.random_order.42` hitting the 600 s ctest timeout under that load; `ctest -R unit.random_order`
  alone passed 3 / 3 (221.7 s total). `capi.c`, `capi.ue_like`, `capi.jolt_step` pass. After merging origin/main (WP-UE-06, Python tools only)
  the editor / game builds (17.7 s / 28.8 s incremental) and two automation runs (5 / 5) were repeated and pass.
- A core rebuild that changes `kspcore_link.txt` (new library or definition) rebuilds the bridge on the next UBT run; the ctest twin must be
  re-run (`Scripts/test.ps1` does it) when `kspcore.lib` changes, or `JoltStep` compares against a stale hash.
- Cooking needs engine assets that are loaded by path to be listed in `DirectoriesToAlwaysCook` (`Config/DefaultGame.ini`); the
  cooker cannot see `LoadObject` strings. Already done for the spike's materials and meshes. Future content should use
  hard or soft references instead.
- `SetNewWorldOrigin`'s `FIntVector` origin limits it to +-21,474 km from the start origin, which is not enough for
  interplanetary scenes. Camera-local placement is the scalable approach.

## Unverified

- Shadows (CSM/VSM), TAA/TSR, Lumen and Nanite at this scale: all off for the iGPU and for clean measurements.
- Niagara/particles, decals and translucency far from the origin. Planet rotation (KSP's rotating frame below 100 km).
  Terrain heights. Chaos joints and contacts far from the origin (only free bodies and teleports were tested).
- Shipping configuration. The Development game was cooked, staged and ran the full spike with jitter metrics identical to
  editor `-game`, so only Shipping is untested. The canonical numbers in RESULTS come from editor `-game`. In a back-to-back
  A/B, the cooked build matched it on render and GPU time and was about 20% faster on game-thread work (origin shifts).
  Runs vary 10 to 20% on this shared laptop.
- Planet-surface jitter is emulated, not imaged. The emulator was validated on the GPU against cubes that use the same
  arithmetic.
