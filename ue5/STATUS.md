# ue5/ STATUS (2026-10-09; WP-UE-01 bridge rebuild 2026-11-13; WP-UE-07 sim subsystem 2026-11-18)

## What works

- **UE 5.8 C++ project `KspUe5`** (no Blueprints): game module `KspUe5`, editor module `KspUe5Editor` (map-generating
  commandlet), plugin `KspCoreBridge`. Builds from the command line for Development Editor and Development Game, Win64, with 0
  warnings in project code. Git repo in `ue5/` with an Unreal `.gitignore` and `.gitattributes` (binary `.uasset`/`.umap`/`.lib`/`.png`).
- **KspCoreBridge** links the real core (WP-UE-01, 2026-11-13): `kspcore.lib` (RelWithDebInfo, `/MD`, IDL 0, C++20) and `Jolt.lib`
  through the **link manifest** the core build writes (`core/build/RelWithDebInfo/kspcore_link.txt`, `file(GENERATE)` in
  `core/src/CMakeLists.txt`; `key=value` lines: `manifest_version`, `config`, `include`, `lib` in link order, `define` for Jolt's
  `JPH_*` configuration). `KspCoreBridge.Build.cs` reads it (env `KSPCORE_LINK_MANIFEST` overrides), so a new core dependency never needs
  a Build.cs edit (the `ue5/Stub` placeholder and its `bUseRealCore` switch were removed by WP-UE-07: the facade needs ABI v2). Both targets (Development Editor, Development Game)
  build from clean with 0 warnings (lines containing "warning" in the UBT logs: 0). The module compiles with `FPSemantics = Precise`
  (property verified in `ModuleRules.cs:784` of the engine's UBT sources); every call into core goes through `FKspFpGuard`, which sets
  MXCSR to 0x1F80 (round to nearest, exceptions masked, FTZ / DAZ off) and restores the caller's value. The core's test-only C ABI
  (`kspcore_test.h`, outside `KSPCORE_ABI_VERSION`) gives the Jolt pile scenario hash, an MXCSR probe and a Jolt configuration probe.
  Jolt needs an AVX2 CPU. Required compiler settings are in README.md.
- **Headless automation tests**: 5 / 5 pass, run twice after the clean builds (`KspUe5.Bridge.LinksCore`, `KspUe5.Bridge.FpGuard`,
  `KspUe5.Bridge.JoltStep`, `KspUe5.Precision.Float32VsLwc`, `KspUe5.Spike.CubeSpherePatch`). `JoltStep`: the pile scenario
  (96 bodies, 200 steps, Jolt double precision) gives state hash `0x0be3de1d6affe387` through the bridge and the same value in its ctest
  twin `capi.jolt_step` (a pure C program on the same test ABI; it writes `core/build/RelWithDebInfo/kspcore_jolt_step.txt`, which
  `Scripts/test.ps1` regenerates before each run); the hash is also identical at 4 threads, run to run, and with the caller's MXCSR set to
  FTZ / DAZ. Jolt is deterministic per binary and call order, not across compilers, so the hash is only compared between processes that
  run the same `kspcore.lib` / `Jolt.lib`; no hash is stored in the repo.
- **Map `/Game/Maps/ScaleSpike`** is generated by code (`-run=KspCreateSpikeMap`). All content is spawned at runtime in C++.
- **Phase-0 scale spike**: runs unattended and deterministically in about 3.5 minutes. It writes CSVs, PNGs and a log, then quits.
  Results are in `spike/RESULTS.md`.

## Sim subsystem, frame loop, placement (WP-UE-07, 2026-11-18)

Core now runs inside Unreal, once per rendered frame, and ends bit for bit where the headless C program ends.

- **Facade** (`Plugins/KspCoreBridge`, `KspSim.h`): `FKspAxis` (Unity Y-up metres <-> UE Z-up centimetres, UE (X, Y, Z) = Unity (Z, X, Y) x 100),
  `FKspGame` (process init + game database, one per process, shut down with the module), `FKspSim` (RAII `kspcore_sim`: new sandbox game,
  launch, scene loaded, input frame, `kspcore_frame`, snapshot hash, and per-frame copies of the frame state, vessels, parts and events
  with positions already in UE axes and centimetres relative to the dominant body). Every call runs under `FKspFpGuard`. The bridge is
  written against ABI v2 (`static_assert`); it is still the only code that includes kspcore headers. Not wrapped yet: commands, bodies, sun,
  terrain quads, camera, node poses, FX (each lands with the package that uses it).
- **`UKspSimSubsystem`** (`Source/KspShell`, a `UWorldSubsystem` of game worlds): owns the sim; an `FTickFunction` in `TG_PrePhysics` runs
  input -> `kspcore_frame` -> snapshot -> events -> render anchor -> placement. A scene load core requests is answered at once
  (`kspcore_scene_loaded`): there are no scene actor sets to build before WP-UE-17. `FixedFrameDt` passes an exact delta to core (gates);
  `InputSource` is the seam the input device of WP-UE-08 binds (unbound: an idle device with focus, the viewport size and real time).
- **Render anchor** (`FKspRenderAnchor`, DESIGN D6): actors go at (position - anchor); the anchor moves to the focus beyond 100 km and at
  every frame change of core. The focus is the active vessel's centre of mass until core has a camera (WP-UE-03). Count and cost are logged.
- **Debug view**: every loaded part's collider proxies (boxes, spheres, capsules as lines; convex hulls as their points) through the new core
  call `kspcore_part_collider_proxies`, cvar `ksp.DrawColliderProxies` (default 1). `Scripts\fly.ps1` starts a sandbox flight in `-game`
  mode from `decompiled\KSP-dev` (`-KspLaunch=<craft>`, default the stock Kerbal X on the LaunchPad) with a fixed chase camera 25 m from
  the vessel; `-Shot <png>` takes a screenshot at a sim frame and quits (`slice/shots/wpue07_pad.png`: Kerbal X on the pad, 73 parts).
  The chase camera and the proxies are stand-ins until WP-UE-09 and WP-UE-10.

## Part rendering, first half (WP-UE-10, 2026-11-18)

Parts are drawn with the game's own meshes and textures, read at run time from `decompiled/KSP-dev` (nothing is cooked or copied).
Screenshot: `slice/shots/wpue10_parts_pad.png` (the stock Kerbal X on the pad; `Scripts\fly.ps1 -Shot ...`).

- **Core** (`core/STATUS.md` "WP-UE-10, core side"): `kspcore_game.h` "part models": the hierarchy `PartLoader.CompileModel` builds below a
  part (rig nodes tied to the nodes of its `.mu` files, MODEL position / rotation / scale, rescaleFactor), the files with their texture
  replacements, and the file behind a GameDatabase texture url.
- **Facade** (`KspModel.h`, `FKspModels`): rigs, the render side of a `.mu` (meshes, renderers, materials, texture references) and texture
  headers, converted once to Unreal's axes and centimetres. Triangle order is flipped (Unity front faces are clockwise); texture
  coordinates stay Unity's, so textures are uploaded in Unity's row order.
- **`UKspPartAssets`** (`Source/KspShell`): one `UStaticMesh` per mesh of a `.mu` file (runtime `BuildFromMeshDescriptions`, fast path, shared
  by every instance); one `UTexture2D` per texture url (DDS DXT1 / DXT5 blocks uploaded as stored with every mip level of the file, MBM
  raw pixels, PNG / TGA / JPEG decoded and flipped; a normal-map request of a readable texture is converted as
  `GameDatabase.BitmapToUnityNormalMap` does); one `UMaterialInstanceDynamic` per model material; one component-tree template per part.
  MODEL texture replacements apply by texture name as in `PartLoader.cs:1932` (to `_MainTex`, `_BumpMap`, `_Emissive`; `_SpecMap` is not sampled
  by the masters yet).
- **Master materials** (`Content/Ksp/Materials`, generated by the `KspCreateMaterials` commandlet, `Scripts\create_materials.ps1`):
  `M_KspOpaque`, `M_KspMasked`, `M_KspTranslucent`, `M_KspAdditive`, `M_KspUnlit`, `M_KspUnlitTranslucent`, the parameter collection `MPC_Ksp`
  (the scene's flat ambient light, default 0.1) and three default textures. All 28 shader names of the stock `.mu` files map to one of
  them (`DepthMask` draws nothing). They are a physically based stand-in with KSP's inputs (main texture and colour, the gloss map in the
  main texture's alpha, the normal map in Unity's layout with x in alpha and y in green, emissive, cutoff, opacity), not KSP's Blinn-Phong
  in gamma space (DESIGN open decision O7). Material colours are converted from gamma to linear values.
- **`UKspSimSubsystem`**: one actor per loaded part (a scene component per model node that draws or has a drawing descendant, a
  `UStaticMeshComponent` per renderer, no collision), re-placed from the snapshot every frame; a white directional light of 10 lux along
  core's sun direction (the stand-in until WP-UE-12). Collider proxies are now a debug overlay (`ksp.DrawColliderProxies`, default 0) and what
  a part without a readable model is shown as. The screenshot waits for the shader compiler.

Kerbin's surface is drawn from the quads core's PQS builds. Screenshot: `slice/shots/wpue11_terrain_pad.png` (Kerbal X on the pad, the

## Input device (WP-UE-08, 2026-11-18)

Keys and mouse reach core, and KSP's own bindings there decide what they do (DESIGN D12). With `Scripts\fly.ps1` the craft can be
flown from the keyboard: Z / X and Shift / Ctrl throttle, T SAS, Space stage, W A S D Q E. Screenshot: `slice/shots/wpue08_liftoff.png`
(Kerbal X off the pad after the scripted keys Z, T, Space; the launch clamps stay behind).

- **`FKspInputDevice`** (`Source/KspShell`): a Slate input pre-processor (before any widget, never consuming) that turns Unreal's key and
  mouse events into one frame of `UnityEngine.Input`-shaped state: keys that went down and up in event order, keys held, mouse buttons as
  KeyCodes and bits, cursor with Unity's origin (bottom left), delta, wheel. A key repeat is not a press; a tap within a frame is down
  and up and never held; losing the window's focus releases everything.
- **Key table**: Unreal `FKey` to `UnityEngine.KeyCode`. 126 KeyCode values are produced by Unreal keys; the other 198 are listed with the
  reason (shifted characters of a US keyboard, keys Unreal does not have, Mac keys, joystick buttons beyond one XInput pad).
- **`UKspSimSubsystem`** owns the device, registers it with Slate when the process has a window and takes its frame every sim frame
  (viewport size, cursor, focus, UI hover = the pointer is not directly over the game viewport). `InputSource` stays as the test seam.
- `-KspKeys=<frame>:<key>,...` on the command line presses keys at sim frames as real Slate key events (`fly.ps1 -Keys`), so a scripted run
  goes through the same path as a keyboard. The session's log ends with the active vessel's altitude and speed.

## Spike verdict (details in `spike/RESULTS.md`)

- **Jitter-free at Kerbin scale: YES**, with LWC alone and no rebasing, provided every primitive stores vertices relative to a
  nearby origin. Measured on the GPU output: 0.000 px at a 100 km orbit, at 1 m above the ground and at 12,000 km (Mun); at most
  0.048 px while strafing 1 mm per frame; 0.000 px pop on a forced origin shift. The Mun renders at 12,000 km and is stable to
  0.11 px with the camera moving at 112 km/s.
- **The one failure mode** is geometry stored far from its primitive origin (for example a planet-centred mesh): 7 to 19 px of
  jitter, and rebasing does not fix it. A UE4/Unity-style float32 pipeline would jitter 5.6 cm (13 to 17 px) at Kerbin's surface
  and 72 cm (207 px) at the Mun. That is the classic reason KSP rebases, and UE 5.8's double-float vertex path removes it. The
  op-for-op emulator of that path was validated against the GPU.
- **Rebasing**: both `UWorld::SetNewWorldOrigin` (manual) and moving every actor work in 5.8. `SetNewWorldOrigin` is cheaper:
  0.23 ms per shift bare, 5.9 ms per shift (+9.1 ms game thread) with 457 bodies + 1,325 colliders, against about 5.5 ms for
  KSP's per-tick shift. Chaos does not support origin shifting, so bodies are teleported one by one, which is about 80% of the
  cost. Recommendation: no per-tick rebasing. Use camera-local placement from the core's doubles, and rebase rarely (about a
  100 km threshold) only where a float-only subsystem needs it.

## What does not work / blockers

- `UnrealBuildTool.exe` cannot be run directly: it needs the .NET 10 runtime, which is not installed system-wide. Workaround in
  place: everything goes through `Build.bat`, which uses the engine-bundled dotnet. Not a blocker.
- Observed once, not reproduced: the very first full automation run in the fresh worktree stalled (the game-thread frame counter stopped
  advancing, no test started) and was stopped after about 6 minutes; five later runs (3 single tests, 2 full) were fine. Cause unknown.
- Fresh core suite (`core/build` deleted, `run_tests.ps1`, 4 jobs, two other agents building): build 1,206 s, ctest 52 / 54 in 897.7 s. The two
  failures were `unit.random_order.27` and `unit.random_order.42` hitting the 600 s ctest timeout under that load; `ctest -R unit.random_order`
  alone passed 3 / 3 (221.7 s total). `capi.c`, `capi.ue_like`, `capi.jolt_step` pass. After merging origin/main (WP-UE-06, Python tools only)
  the editor / game builds (17.7 s / 28.8 s incremental) and two automation runs (5 / 5) were repeated and pass.
- A core rebuild that changes `kspcore_link.txt` (new library or definition) rebuilds the bridge on the next UBT run; the ctest twin must be
  re-run (`Scripts/test.ps1` does it) when `kspcore.lib` changes, or `JoltStep` compares against a stale hash.
- Cooking needs engine assets that are loaded by path to be listed in `DirectoriesToAlwaysCook` (`Config/DefaultGame.ini`); the
  cooker cannot see `LoadObject` strings. Already done for the spike's materials and meshes. Future content should use
  hard or soft references instead.
- `SetNewWorldOrigin`'s `FIntVector` origin limits it to +-21,474 km from the start origin, which is not enough for
  interplanetary scenes. Camera-local placement is the scalable approach.

## Unverified

- Shadows (CSM/VSM), TAA/TSR, Lumen and Nanite at this scale: all off for the iGPU and for clean measurements.
- Niagara/particles, decals and translucency far from the origin. Planet rotation (KSP's rotating frame below 100 km).
  Terrain heights. Chaos joints and contacts far from the origin (only free bodies and teleports were tested).
- Shipping configuration. The Development game was cooked, staged and ran the full spike with jitter metrics identical to
  editor `-game`, so only Shipping is untested. The canonical numbers in RESULTS come from editor `-game`. In a back-to-back
  A/B, the cooked build matched it on render and GPU time and was about 20% faster on game-thread work (origin shifts).
  Runs vary 10 to 20% on this shared laptop.
- Planet-surface jitter is emulated, not imaged. The emulator was validated on the GPU against cubes that use the same
  arithmetic.
